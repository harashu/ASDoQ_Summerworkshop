# テスト（回帰テスト用の文書と正解）

欠陥を意図的に仕込んだ文書と、その正解です。ペルソナの追加や判定役の追加が本当に効果があるかを、数字で確かめるために使います（設計書の「評価（テスト）計画」を参照）。

## テストケース

| ケース | 文書種別 | 欠陥 | 正しい記述 |
|---|---|---|---|
| [case01_srs](cases/case01_srs/) | 要求仕様書 | 48件（仕込み44件＋レビューで発見4件。17副特性すべて） | 4件 |
| [case02_blockbreaker](cases/case02_blockbreaker/) | 要求仕様書（ブロック崩しゲーム。ワークショップ教材） | 87件（17副特性すべて。改訂案 `answer_key_original.md` の下線部を1件ずつ変換） | 1件 |

case02 の `accepted_sub_characteristics` は改訂案の分類だけにしています。分類正解率は「改訂案の分類との一致率」として読んでください。

各ケースのフォルダには次のファイルがあります。

| ファイル | 内容 |
|---|---|
| `document.md` | レビュー対象の文書 |
| `meta.json` | 文書のメタ情報（文書種別・目的・読者・社外か・海外か など） |
| `answer_key.json` | 正解（機械照合用の正本） |
| `answer_key.md` | 正解一覧（人が読む用） |

## 照合のルール

レビューの指摘（最終レビューの項目、またはペルソナの指摘）を、次のどちらかを満たすときに正解の欠陥に対応付けます（「検出」と数えます）。

1. **引用が一致し、かつ中身も合っている**
   - 引用の一致：指摘の `quote` と欠陥の `match_texts` のどれかについて、どちらかがもう一方を含む（短い引用は、相手の半分以上の長さが必要）。
   - 中身の一致：指摘の副特性が `accepted_sub_characteristics` に含まれる、または指摘文（`issue`・`raw_comment`）に `evidence_any` の語のどれかを含む。
   - 同じ文に複数の欠陥が入っていることがあるため、引用の一致だけでは検出と数えません。
2. **引用が違っても、指摘文に `mention_any` の具体的な語を含む**
   - 書かれていないことの欠陥（`match_texts` が空）や、別の指摘にまとめて書かれた欠陥を拾うためのルールです。
   - 誤判定を避けるため、`mention_any` にはその欠陥に固有の具体的な語だけを入れます。

**分類正解率**は、検出した欠陥のうち、指摘の副特性が `accepted_sub_characteristics` に含まれていた割合です。

レビューで見つかった妥当な指摘で、正解表にないものは、人が確認したうえで `source` に「レビューで発見」と書いて追加します。

## 測る指標

| 指標 | 計算 | 見たいこと |
|---|---|---|
| 検出率 | 検出した欠陥数 ÷ 正解の欠陥数 | 見落としの少なさ |
| 分類正解率 | 分類も正しかった数 ÷ 検出した欠陥数 | ASDoQの副特性を正しく使えているか |
| 誤検出数 | 正しい記述（N01〜N04）への指摘数 | 余計な指摘をしていないか |
| 対応なしの指摘数 | どの欠陥にも対応しない指摘数 | 仕込んでいない本当の問題か、誤検出か（**人が目で確認する**） |
| 重要度の順位相関 | 最終スコアの順位と `expected_severity` の順位の相関 | 重み付けが妥当か |
| 知識の反映率 | `knowledge_refs` がある欠陥のうち、その知識IDを引用して補正した割合 | 知識ベースが効いているか |
| ペルソナごとの独自検出数 | そのペルソナだけが見つけた欠陥の数 | パネルに残す価値があるか |

## 注意

- テスト文書には、意図していない問題が含まれている可能性があります。「対応なしの指摘」は、すぐに誤検出と決めつけず、人が確認してください。本当の問題なら `answer_key.json` に追加します。
- LLMの出力は毎回変わるため、同じ構成で3回以上実行して平均を見てください。
- 同じテスト文書を何度も使ってプロンプトを調整すると、その文書に過剰に合わせてしまいます。調整用と確認用で別のケースを用意するのが理想です。
