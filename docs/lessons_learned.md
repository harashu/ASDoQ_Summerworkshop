# 試行の記録と知見

テスト文書 `tests/cases/case01_srs`（要求仕様書・欠陥48件・正しい記述4件）を使って、構成を変えながら試した記録です。3回とも、APIキーなしの手順（[run_with_claude_code.md](run_with_claude_code.md)）で実行しました。数値は、2026-09-26 時点の正解表と照合ルールで、3回分を同じ条件で照合し直したものです。

## 1. 3回の試行の比較

| 項目 | 1回目 | 2回目 | 3回目（現在の構成） |
|---|---|---|---|
| パネル | 6人（A11, A05, A01, A07, A03, A09） | 7人（＋B08 細かい人） | 7人（B08 を標準パネルに） |
| 軽微な指摘の欄 | なし（詳しい指摘10件まで） | あり（最大10件） | あり（最大5件） |
| ペルソナの指摘数 | 60 | 143 | 109 |
| 最終レビューの項目数 | 33 | 52 | 45 |
| **検出率（最終）** | 37/48（77%） | **48/48（100%）** | 43/48（90%） |
| 分類正解率（最終） | 92% | 90% | **98%** |
| 誤検出（正しい記述への指摘） | 0 | 1 | **0** |
| 目視確認が必要な項目 | 0 | 6 | 4 |
| 重要度の順位相関 | 0.45 | 0.62 | 0.62 |
| 知識の反映率 | 70% | 69% | 73% |

| 統合にかかった時間 | 約8分 | 約10.5分 | **約7分** |

**現在の構成（3回目）を採用した理由**：検出率は2回目より少し下がりますが、誤検出がなく、分類の正確さが最も高く、ノイズと処理時間も少ないため、全体のバランスが最もよいと判断しました。

## 2. わかったこと

### ペルソナについて

- **人格は機能する。** 同じ文書でも、立場によって見つけるものと言い方がはっきり分かれた。3回とも全員が指摘したのは「保存期間の矛盾」だけだった。
- **独自の発見が多いのは A07 半年後の後任と A09 非ネイティブ。** 経緯・参照の欠落と、翻訳で崩れる日本語は、ほかのペルソナではほとんど拾えなかった。
- **B08 細かい人がいないと、記法適合性（誤字・箇条書きの記号など）は検出できない。** 1回目は記法適合性が0件だった。
- **A11 冷静な品質責任者が独自に見つける欠陥は少ない。** ただし、統合時に分類の基準として使われ、分類の正確さを支えている（想定どおりの役割）。
- **指示していない人格も表れた。** A01 意地悪な顧客は、修正案を空欄にすることが多かった（「直し方は御社が考えること」という振る舞い）。
- **仕込んでいない本物の問題も見つかった**（D45〜D48）。「稼働率」の意味の違い、対象外の範囲がないこと、海外の法令・個人情報の扱い、運用ルールの混入。

### 出力の件数について

- **件数の上限があると、気づいた問題を捨てる。** 1回目、A11 はメモに表記の問題を6件書いていたのに、上限10件のために指摘から外していた。
- **軽微な指摘の枠を設けると、ほぼ全員が上限まで埋める。** 最大10件にしたら指摘数が2倍以上になり、誤検出や価値の低い項目が増えた。最大5件にして「枠を埋めるために無理に探さない」と書くと、ノイズが減った。

### ポカヨケ（コードでの検査）について

- **引用の捏造は3回とも0件だった。** 引用が文書に実在するかの検査は、今のところ除外の出番がないが、保険として残す。
- **副特性の欄に品質特性名を混ぜる誤りを、1件検出して除外できた**（3回目の「非曖昧性（識別性）／可読性」）。
- **オーケストレーターのスコア計算は、3回とも全項目がコードの再計算と一致した。**

### オーケストレーターについて

- **「ペルソナが挙げていない問題は最終レビューに足さない」というルールを守る。** その結果、オーケストレーター自身が気づいた問題（3回目の要求IDなし、開発体制の記述）は、統合方針のメモにしか残らなかった。透明性とのトレードオフになっている。
- **知識による補正の幅を、自分で決めている。** 3回とも「必須は +1.0、推奨は +0.5」程度の基準を自分で置いていた。指示書に目安を書いておくと、試行ごとのぶれが減るはず。
- **K-CUS-02（海外工場向けの書き方）は3回とも使われなかった。** 対象文書を「手順書・取扱説明書」に限定していたため。知識の対象範囲の書き方が、重み付けに直接効く。

### 評価（照合）について

- **引用の一致だけで検出と数えると誤る。** 同じ文に別の欠陥が入っていることがあるため、指摘の中身（副特性またはキーワード）も確認するルールにした。
- **キーワードの書き方ひとつで照合結果が変わる。** 「読み手、」「読み手（」が一覧になかったため、実際には検出していた D02 を見逃し扱いにしていた。照合で見逃しと出たものは、人が中身を確認してから結論を出す。
- **試行ごとのぶれがある。** D33（MTBFの未定義）や D45（稼働率の意味）は、検出される回とされない回がある。構成を比べるときは、同じ構成で3回以上実行して平均を見る必要がある。

## 4. ブロック崩しゲーム要求仕様書（case02、ワークショップ教材）での試行

教材の不完全な要求仕様書と、その改訂案（87件の欠陥。1文ごとに欠陥が入っている密度）で試した。パネルは要求仕様書の標準パネル5人＋A09の6人（社内向けなので A03 は入らない）。

| 項目 | 1回目（判定役なし） | 2回目（＋層2 判定役） |
|---|---|---|
| ペルソナの出力 | 新規 | 1回目と同じもの（判定役の効果だけを比べるため） |
| 指摘数（ペルソナ＋判定役） | 95 | 106（判定役の追加 11） |
| 最終レビューの項目数 | 57 | 73 |
| **検出率（最終）** | 61/87（70%） | **66/87（76%）** |
| 分類正解率（改訂案の分類との一致） | 80% | 82% |
| 誤検出 | 0 | 0 |
| スコアの再計算チェック | 全項目一致 | 全項目一致 |
| 統合にかかった時間 | 約10分 | 約12分（＋判定役 約1.5分・並列） |

わかったこと：

- **欠陥の密度が高い文書では、件数上限が検出率の上限になる。** 6人の枠は合計95件で、87件の欠陥に対して重複を考えると足りない。case01（48件）の90%に比べて低いのは主にこのため。
- **判定役は「誰も挙げなかった欠陥」を拾った。** 追加11件のうち5件が新規の検出で、未定義の略語、論理展開の順序、記述間の論理的な衝突、対象を特定できない記述、図の記法にわたっていた。分類の判定は、再分類・移管が4件だった。
- **判定役は「漏れの確認」で『未確認の副特性はない』と答えたが、実際には21件の見逃しが残った。** 副特性ごとに1件でも指摘があれば「指摘あり」になるため、同じ副特性の中の別の欠陥の見逃しまでは確認できていない。
- **見逃しの多くは、1語レベルの言葉づかい**（助詞の選び方、漢字とひらがなの使い分け、範囲の書き方、文として成り立っていない文など）。細かい言葉づかいの欠陥が大量にある文書では、B08 の枠だけでは足りない。
- **分類の判定の境界は、正解と一致しないものがある。** 例えば、正解では保守性（再利用性）に分類されている表記の問題を、ペルソナは可読性（表記適切性）や理解容易性（一意性）に分類した。副特性の境界は、ワークショップで議論する材料になる。
- **重大な指摘がスコアで上位に来ないことがある。** 重大度5の指摘でも、確信度が低いと2点台になる。引用できる知識がないと補正できないため、知識ベース（会社テンプレ・法令の必須事項）を増やすと改善できる。
