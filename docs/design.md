# 文書レビューエージェント 設計書

Anthropic「Building effective agents」の設計3原則に基づいて、ASDoQ文書品質モデルによるマルチペルソナ文書レビューエージェントを設計する。

参考：https://www.anthropic.com/engineering/building-effective-agents

## 1. 設計3原則とこのシステムでの解釈

| 原則 | 原文 | このシステムでの具体化 |
|---|---|---|
| 1. シンプルさ | Maintain simplicity in your agent's design | 自律エージェントではなく、**決まった順序で流れるワークフロー**にする。計算で済む処理はコードで行い、LLMは判断が必要な処理だけに使う。ペルソナは少人数から始め、効果が確認できたものだけを増やす |
| 2. 透明性 | Prioritize transparency by explicitly showing the agent's planning steps | パネル選定の理由、重み付けの計算式、知識による補正の根拠、困った人型の指摘の言い換えを、すべて「判断の記録」として出力する |
| 3. ACIの作り込み | Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing | ペルソナとオーケストレーターの間のJSON形式、知識ベースの形式を厳密に定義する。誤りをコードで自動検出する（ポカヨケ）。欠陥を仕込んだ文書で回帰テストを行う |

## 2. 全体構成：ワークフローとして設計する

記事の区別では、LLMが自分で手順を決めるものが「エージェント」、あらかじめ決めた手順でLLMを動かすものが「ワークフロー」である。文書レビューは手順が毎回同じなので、**ワークフローで十分**である（原則1）。

「指揮者（オーケストレーター）」という名前は残すが、記事の Orchestrator-Workers パターン（タスクを動的に分解する）ではない。実際には次の3つのパターンの組み合わせである。

### 層と役割

社内のレビュー会議にたとえると、次の構成になる。

| 層 | たとえ | やること | 知っていること | 知らないこと・やらないこと |
|---|---|---|---|---|
| オーケストレーター | 議長 | 前半：パネル選定。後半：知識による重み付け、困った人型の言い換え、修正案、最終レビューの作成 | 知識ベース、ペルソナの人格情報（フロントマター）、判定結果 | 文書にない問題を新しく足さない |
| 層1 ペルソナレビュアー | 会議の参加者 | 立場と性格に基づいて、品質特性をまたいで指摘する（並列） | 自分の人格、ASDoQモデル、文書 | 知識ベース、他ペルソナの指摘、自分が割り引かれること |
| 事務局（コード） | 事務局 | 形式の検証、引用の実在確認、基礎スコアの計算、特性ごとの仕分け | 計算式、公式名称の一覧 | 判断はしない |
| 層2 特性別の判定役 | ASDoQの審判（6人） | 担当特性について、分類の確認、同じ問題のグループ化、漏れの確認（並列） | 担当特性の副特性・測定項目、見分け方、文書 | 人格情報、知識ベース。重要度を変えない。指摘の文章を書き換えない |

- **ペルソナを品質特性の下に置かない。** ペルソナは品質特性をまたいで指摘する（多対多）ため、フラットに並べる。品質特性の軸は、層2の判定役が担う。
- **重み付けはオーケストレーターの1か所だけで行う。** 判定役に人格情報や知識を持たせないのは、補正の二重掛けを防ぎ、どこでスコアが変わったかを追えるようにするため（原則2）。
- **判定役は指摘の文章を書き換えない。** 要約を重ねると元の発言が薄れる（伝言ゲーム）ため、グループ化と判定だけを行う。
- **層2は最初は省略する。** テストで分類の誤りが多い、または指摘の数が多く1回の統合で扱いきれないとわかったら追加する（原則1）。

### ステップ

| ステップ | 記事のパターン | 処理 | 担当 |
|---|---|---|---|
| 1. パネル選定 | Routing（振り分け） | 文書種別に応じてペルソナを選ぶ | **コード**（標準パネル表）＋ 必要なときだけLLM |
| 2. ペルソナレビュー | Parallelization / Sectioning（並列・観点分割） | 各ペルソナが並列にレビューする | LLM × 4〜6 |
| 3. 検証・スコア計算・仕分け | ―（ポカヨケ） | JSONの検証、引用の実在確認、基礎スコアの計算、特性ごとの仕分け | **コード** |
| 4. 特性別の判定（任意） | Parallelization / Sectioning | 6特性ごとに分類確認・グループ化・漏れ確認 | LLM × 6。**テストで必要性が確認できたら追加** |
| 5. 統合・最終レビュー | Parallelization / Voting ＋ Prompt Chaining | 重複の統合、困った人型の言い換え、知識による補正、最終レビューの作成 | LLM（オーケストレーター） |

```
文書 + メタ情報
   │
   ▼
[1] パネル選定 ──── 標準パネル表（コード）→ 不明な文書種別のみLLMで選定
   │
   ▼
[2] 層1 ペルソナ ×4〜6 並列レビュー（LLM）
   │   各自 <analysis> で考えてから <result> JSON を出力
   ▼
[3] 事務局（コード）
   │   ・JSON形式／列挙値／副特性と特性の親子関係
   │   ・quote が文書中に実在するか（捏造の検出）
   │   ・基礎スコアの計算、品質特性ごとの仕分け
   ▼
[4] 層2 特性別の判定役 ×6 並列（任意・LLM）
   │   分類の確認／同じ問題のグループ化／漏れの確認
   ▼
[5] オーケストレーター：統合（LLM）＋ 知識ベース
   │   <plan> 統合方針 → <final_review> 最終レビュー → <trace> 判断の記録
   ▼
最終レビュー ＋ 判断の記録
```

## 3. ステップ1：パネル選定

### 標準パネル表（コードで持つ）

- **A11 冷静な品質責任者は常に入れる。** 他のペルソナの分類と重大度を較正する基準線になるため。
- **C群（困った人型）は最大1人。** 多いとノイズが増えるため。
- **パネルは合計4〜7人。** 要求仕様書・設計書には B08 細かい人を標準で入れる（2026-09-26 の試行で、B08 がいないと記法適合性の欠陥を1件も検出できなかったため）。

| 文書種別 | 標準パネル | C群（任意） |
|---|---|---|
| 要求仕様書 | A11, A05 実装者・テスター, A01 意地悪な顧客, A07 半年後の後任, B08 細かい人 | C04 後出しじゃんけん |
| 設計書 | A11, A05 実装者・テスター, A07 半年後の後任, B03 ロジックの鬼, B08 細かい人 | C06 担当しか見ない人 |
| 手順書・取扱説明書 | A11, A06 現場の運用担当, A08 初見の新人, B04 心配性 | C07 言いっぱなし |
| 議事録・メール | A11, A07 半年後の後任, B02 本質を突く人 | C09 揚げ足取り |
| 企画書・提案書 | A11, B02 本質を突く人, A02 多忙な役員, B01 ジョブズ | C04 後出しじゃんけん |
| 報告書 | A11, A02 多忙な役員, B05 数字で示せ, B03 ロジックの鬼 | C01 遠回し |

### 追加ルール（コード）

- 社外に出る文書なら A03 法務担当 を追加する。
- 海外拠点・海外顧客に渡るなら A09 非ネイティブ を追加する。
- 認証・監査の対象なら A04 監査人 を追加する。
- ナレッジベースに登録するなら A10 生成AI・RAG を追加する。

文書種別が表にない場合だけ、`prompts/orchestrator/01_panel_selection.md` でLLMに選ばせる。

## 4. ステップ3：検証とスコア計算（コード）

### 検証ルール（ポカヨケ）

| 検査 | 失敗したときの扱い |
|---|---|
| JSONとして読み込めるか | そのペルソナに1回だけ再実行させる |
| `characteristic` と `sub_characteristic` が公式の名称か | 1回だけ再実行させる |
| `sub_characteristic` が `characteristic` の子か（例：関係性 → 理解容易性） | 親の特性をコードで正しい値に直し、`auto_fixed` を記録する |
| `quote` が文書中に実在するか（空白を除いて部分一致） | 指摘を除外し、「引用が見つからない」として判断の記録に残す。C04 後出しじゃんけんのように「書かれていないこと」を指摘する場合は、`quote` が空でもよい |
| `severity` が1〜5、`confidence` が0〜1か | 範囲内に丸める |

### 基礎スコアの計算式

計算はコードで行い、式を判断の記録に載せる（原則2）。

```
補正後重要度 = clamp(severity − severity_bias, 1, 5)
重点係数     = 1.0（指摘の特性が focus で 0.2 以上）／ 0.7（それ以外）
基礎スコア   = 補正後重要度 × base_reliability × 重点係数 × confidence
```

`severity_bias`・`base_reliability`・`focus` は、各ペルソナファイルのフロントマターから読む。

## 5. ステップ4：特性別の判定（任意・LLM）

プロンプトは `prompts/judges/characteristic_judge.md`。1つのテンプレートに特性名を差し込んで、6特性で共通に使う。

- 判定結果（`妥当`・`再分類`・`移管`・`根拠不足`・`未決定`）はコードで指摘に反映する。`移管` の指摘は移管先の特性に付け替える。
- `根拠不足` の指摘は除外せず、オーケストレーターに判定理由付きで渡す（採否はオーケストレーターが決める）。
- 判定役が追加した指摘（`J-` で始まるID）も、ペルソナの指摘と同じ検証（引用の実在確認）にかける。基礎スコアの計算では `base_reliability` を 0.9、`severity_bias` を 0、重点係数を 1.0 とする。

## 6. ステップ5：統合（LLM）

オーケストレーターだけが知識ベースを読む。判断が必要な処理だけを担当する。

1. **重複の統合**：同じ箇所・同じ問題の指摘をまとめる。複数のペルソナが独立に同じ問題を挙げたら、合意ボーナスを加える（Voting）。
2. **困った人型の言い換え**：`orchestrator_hint` に従って真意を取り出し、行動できる指摘に書き直す。原文と言い換えの両方を記録する。
3. **副特性の再分類**：共通プロンプトの見分け方に照らして分類を確認し、変えた場合は理由を記録する。
4. **知識による補正**：会社テンプレ・業界ノウハウ・顧客特性に照らしてスコアを上下させる。**必ず知識のIDを引用する。** 引用できない補正はしない。
5. **修正案の作成**：`suggestion` が null の指摘に修正案を付ける。
6. **良い点の保護**：修正案が、挙がった良い点を壊さないか確認する。

### 最終スコアの計算式

```
最終スコア = 統合元の基礎スコアの最大値
           + 合意ボーナス（0.5 ×（独立に指摘したペルソナ数 − 1）、上限 1.5）
           + 知識補正（−2.0〜+2.0。知識IDの引用が必須）
```

LLMは各項目の計算内訳を `<trace>` に出す。コードで再計算して一致を確認する（ポカヨケ）。

## 7. 知識ベースの形式（ACI）

`knowledge/` に置く。オーケストレーターが引用できるように、**1項目ごとにIDを付ける。**

| ファイル | ID接頭辞 | 内容 |
|---|---|---|
| `company_template.md` | `K-TPL-` | 社内テンプレートの必須章・記述ルール |
| `domain_knowhow.md` | `K-DOM-` | 業界の規格・過去のトラブル事例・慣習 |
| `customer_profile.md` | `K-CUS-` | 顧客の特性・重視点・過去の指摘傾向 |

## 8. ペルソナとのインターフェース（ACI）

記事の助言に従って、次の点を作り込む。

- **書く前に考える余地を与える**：ペルソナは `<analysis>` で文書を読んだメモを書いてから、`<result>` にJSONを出力する。
- **形式はモデルに自然なものにする**：引用・コメントは短い日本語の文字列とし、JSON内に長文や改行を入れない。
- **誤用しにくくする**：特性と副特性は公式名称の列挙値に限り、親子関係はコードで検査する。
- **件数上限で指摘を捨てさせない**：詳しい指摘（`findings`）は最大10件とし、上限を超えて気づいた問題は軽微な指摘（`minor_findings`、口調・修正案なし、最大5件）として短く出させる。コードは同じ検証とスコア計算を行い、IDを `A11-m1` の形にする（2026-09-26 の試行で、上限のために表記の問題を捨てていたことが判明したため追加）。
- **モデルの立場で試す**：ペルソナごとに、次のテストで出力を目で確認する。

## 9. 評価（テスト）計画

複雑さは「効果が実証されたときだけ」足す（原則1）。

1. **欠陥を仕込んだテスト文書を作る**：17副特性のそれぞれに対応する欠陥を、既知の正解として仕込む（例：表の空欄、直示表現「前回」、TBDの決定時期なし）。
2. **最小構成から始める**：A11 ＋ 標準パネル3人でレビューし、検出率（仕込んだ欠陥のうち見つけた割合）と誤検出を測る。
3. **ペルソナを1人ずつ追加して比較する**：そのペルソナだけが見つけた欠陥がなければ、パネルから外す。
4. **ステップ5（最終チェック）も同じ基準で判断する**：分類の誤りや根拠のない指摘が一定以上残る場合だけ追加する。
5. **困った人型の効果を測る**：C群を入れた場合と入れない場合で、言い換え後の指摘の中に独自の発見があるかを比べる。

## 10. 実装の方針

- フレームワークは使わず、**LLM APIを直接呼ぶ**ところから始める（記事の推奨）。プロンプトと応答を直接確認できるようにするため。
- ペルソナの並列実行、検証、スコア計算は、数十行のスクリプトで書ける。
- 実装は `runner/`（`review.py`：実行、`evaluate.py`：正解との照合）。使い方は [runner/README.md](../runner/README.md)。
