# 「Building effective agents」の要点と、このプロジェクトでの使い方

出典：Anthropic「Building effective agents」 https://www.anthropic.com/engineering/building-effective-agents

この文書は、上記の記事の要点を日本語でまとめたものです（2026-09-26 時点で参照）。正確な内容は原文を確認してください。

## 1. 設計の3原則（記事の結論）

| 原則 | 意味 | このプロジェクトでの具体化 |
|---|---|---|
| ① シンプルさ | エージェントの設計をシンプルに保つ | 自律エージェントではなくワークフローにする。計算・検証はコードで行う。ペルソナや判定役は、効果がテストで確認できたものだけ足す |
| ② 透明性 | エージェントが計画した手順を明示的に見せる | 統合方針（plan）、判断の記録（trace）、スコアの計算内訳を必ず出力する。知識で補正するときは知識IDを引用させる |
| ③ ACI（エージェントとツールの受け渡し口）の作り込み | ツールや入出力の仕様をドキュメントとテストで丁寧に作る | 出力形式をJSONで厳密に決め、引用の実在・副特性の名称・スコアをコードで検査する（ポカヨケ）。欠陥を仕込んだテスト文書で回帰テストする |

## 2. 「ワークフロー」と「エージェント」の区別

- **ワークフロー**：あらかじめ決めた手順（コード）で LLM とツールを動かす。予測しやすい。
- **エージェント**：LLM が自分で手順を決めて進める。柔軟だが、予測しにくく、コストもかかる。
- 記事の考え方：**まずは単純な方法から始め、複雑にするのは効果が実証されたときだけ。** 文書レビューは手順が毎回同じなので、ワークフローで十分。

## 3. 記事が紹介する5つのパターン

| パターン | 内容 | 向いている場面 | このプロジェクト |
|---|---|---|---|
| Prompt Chaining（段階処理） | 仕事を順番のあるステップに分け、前の出力を次の入力にする | 決まった手順を正確にこなしたいとき | ペルソナ → 検証 → 統合 の流れ |
| Routing（振り分け） | 入力を分類して、専用の処理に振り分ける | 入力の種類ごとに扱いを変えたいとき | 文書の種類でパネルを選ぶ |
| Parallelization（並列処理） | 分担して並列に実行する（Sectioning）／同じ仕事を複数回やって多数決する（Voting） | 速さや、複数の視点による信頼性がほしいとき | ペルソナの並列レビュー、合意ボーナス |
| Orchestrator-Workers | 中心の LLM が仕事を動的に分解して任せる | 事前に分け方が決められない仕事 | **使っていない**（名前は「指揮者」だが中身はワークフロー） |
| Evaluator-Optimizer（評価と改善） | 生成と評価を繰り返して改善する | 明確な評価基準があるとき | 層2の判定役・最終チェックとして、必要になったら追加 |

## 4. ツール・入出力の設計（ACI）についての助言

- **モデルの立場で考える**：説明を読んだだけで正しく使えるか。人間向けの画面設計（HCI）と同じくらい手間をかける。
- **書く前に考える余地を与える**：いきなり形式ばった出力をさせず、先に考えを書かせる（このプロジェクトでは `<analysis>` → `<result>` の順）。
- **形式はモデルが見慣れたものに近づける**：エスケープが多い形式や、行数を数えさせる形式は避ける。
- **ポカヨケ**：間違った使い方をしにくい設計にする（このプロジェクトでは、公式名称の列挙、親子関係の自動修正、引用の実在確認）。

## 5. フレームワークについての注意

- フレームワークは便利だが、裏で送っているプロンプトや応答が見えにくくなる。
- まずは LLM の API を直接呼ぶところから始める（このプロジェクトの `runner/review.py` はこの方針）。
- 使う場合も、中で何をしているかを理解しておく。
